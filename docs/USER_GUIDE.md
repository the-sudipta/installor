# Installor User Guide

This guide explains the complete v0.2.0 workflow. Installor manages a software catalog and invokes trusted package managers or installers; it does not replace the operating system's security decisions.

## 1. Installation

### Windows

Download the `.exe` installer from the [latest GitHub release](https://github.com/the-sudipta/installor/releases/latest). The `.msi` is suitable for environments that prefer Windows Installer packages. A standalone executable is provided for portable evaluation.

Because v0.2.0 is not code-signed, Windows may display a SmartScreen warning. Verify that the file came from the official release, compare its SHA-256 value with `SHA256SUMS.txt`, and make your own trust decision before continuing.

### macOS and Linux

Use packages generated by the repository's tagged-release workflow. Platform-specific signing, notarization, and real-hardware QA are not claimed for v0.2.0. For source builds, follow [CONTRIBUTING.md](../CONTRIBUTING.md).

## 2. First launch

Installor creates a per-user SQLite database named `installor.sqlite3`. Open **Settings** and review:

- **Device name:** a human-readable unique name such as `Office Desktop` or `Research Laptop`; Installor uses these names as catalog device categories.
- **Download folder:** where downloaded installers are stored. The default is the user's Downloads directory under an `Installor` subfolder.
- **Search download subfolders:** opt in only if installer files may be nested below the selected folder.

## 4. Detect installed applications

1. Open **Detected software**.
2. Select **Scan this computer**.
3. Review the filtered results.
4. Use the checkboxes to approve the applications you want to manage.
5. Choose **Add selected to catalog**, or **Add all** when every remaining result is appropriate.

**Add to catalog** converts temporary scan results into durable records. It creates or reuses a portable catalog entry and records the detected version and path under this device's saved name. Scanning alone saves and uploads nothing. Use **Select visible** after filtering when you want to approve a group without selecting every scan result.

On Windows, results come from user-facing registry uninstall entries. On macOS, they come from `system_profiler`. On Linux, Installor queries the package tools present on the system. Detection is not proof of license status, provenance, or update availability.

## 5. Import any publicly shared Google Sheet

### Prepare the Sheet

1. Create or open a Google Sheet in any Google account.
2. Create a tab named exactly `Catalog`.
3. Import or copy the header row from [`CATALOG_TEMPLATE.csv`](CATALOG_TEMPLATE.csv).
4. Add rows. The `name` column is required; all other columns are optional.
5. Select **Share → General access → Anyone with the link → Viewer**.
6. Select **Copy link**.

### Import it

1. In Installor open **Settings**.
2. Paste the normal Google Sheets Share URL into **Google Sheet share URL**.
3. Select **Import shared Sheet**.
4. Return to **Catalog** and review every imported source, URL, argument, and checksum before installing.

This works with a Sheet owned by another person or organization. The owner does not connect Installor, create an OAuth application, share a password, or grant account access. The Sheet is accessible because its owner made it publicly viewable; anyone possessing the link may be able to read it. Do not place secrets or private records in that Sheet.

An optional `Installations` tab may use [`INSTALLATIONS_TEMPLATE.csv`](INSTALLATIONS_TEMPLATE.csv). Public import never writes back.

## 6. Download selected software

1. Select one or more catalog rows.
2. Select **Download selected**.
3. Wait for the progress indicator and result message.
4. Investigate every failed download or checksum mismatch.

Never work around a checksum mismatch by deleting the expected value without first determining whether the publisher changed the file, the catalog is stale, or the download was altered.

## 7. Match local installer files

Choose **Find installers** to scan the configured download folder. Installor normalizes names and displays the strongest filename matches; it does not open or trust those files automatically. Confirm a match only after checking its source, filename, signature where available, and version.

## 8. Install selected software

1. Select rows that are ready.
2. Select **Install selected**.
3. Review the number of applications in the confirmation.
4. Approve legitimate operating-system prompts.
5. Review the completion/failure summary.

Installor runs installations sequentially. Native managers receive structured argument arrays, while custom formats use known silent switches or an interactive launch. A successful process exit does not guarantee that every application-specific post-install requirement has been completed; verify critical software after installation.

## 9. Optional bidirectional Google Sheet sync

### Configure the write-back bridge

1. Open the target Google Sheet and keep it in the account whose owner will deploy the bridge.
2. In Installor open **Settings → Set up Google synchronization**.
3. In the Sheet choose **Extensions → Apps Script**.
4. In Installor choose **Copy complete script**. The bundled script is version-matched and already contains a randomly generated secret stored in the OS credential vault.
5. Replace the Apps Script editor's placeholder code, save it, and choose **Deploy → New deployment → Web app**.
6. Set **Execute as** to **Me** and **Who has access** to **Anyone**, deploy, and copy the URL ending in `/exec`.
7. Paste that URL into Installor and choose **Save and test connection**.
8. Choose **Push entire local library** to upload records that existed before setup.

The bridge automatically creates `Catalog`, `Installations`, and `Installor Deletions` tabs when needed. Do not edit or remove the deletion tab unless you are deliberately resetting synchronization history.

### Named device → Google Sheet → another named device

1. On a device named **Office Desktop**, scan, select, and add the desired applications to the catalog.
2. Choose **Sync with Sheet**. Installor uploads pending catalog records under the **Office Desktop** device category.
3. On **Research Laptop**, save that distinct device name and configure the same Apps Script deployment and secret.
4. Choose **Sync with Sheet**. The laptop downloads the catalog and shows categories such as **Office Desktop**.
5. Scan **Research Laptop** if you also want its installed-software state recorded, approve the results, and synchronize again.

The synchronization report separates downloaded catalog rows, downloaded installation rows, uploaded catalog rows, uploaded installation rows, and removals. Sync never scans a computer or performs an installation. Local queued changes survive network failures and retry later. Newer timestamps win; pending deletions take precedence so a removed item cannot reappear from an older remote list.

Rotate the secret and redeploy if it is exposed. Never post it in an issue, public Sheet, or repository.

## 10. Remove records

Select catalog rows and choose **Remove selected**. The confirmation deliberately states the safety boundary: removal deletes Installor catalog and linked installation metadata, but it does not uninstall applications or delete installer files. With write-back configured, deletion markers are queued for the next sync and applied on other connected computers.

## 12. Data and uninstall

Removing Installor through the operating system removes the application but may preserve per-user data. If you intentionally want a complete reset, first export or document anything needed, close Installor, and remove its app-data directory and the `com.installor.desktop` credential entry using your operating system's supported tools. Paths vary by platform; do not delete broad parent directories.

Downloaded installers remain in the configured download folder until the user removes them.

## 13. Platform status and limitations

- Windows v0.2.0 was built, launched, and automatically tested locally.
- Parser and installation-plan tests cover macOS and Linux behavior, and CI is configured for native runners.
- Real DMG deployment, distribution-specific package installation, platform signing, and organization-scale policy evaluation remain manual validation items.
- Installor is an orchestration tool, not an endpoint-management, vulnerability-management, or license-compliance product.
